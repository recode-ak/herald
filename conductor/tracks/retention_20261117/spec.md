# Очистка БД herald — spec

Утверждено Нурболатом 2026-11-17.

## Обзор

В базе herald только оперативные данные: сессии, вопросы, входящие, связи с сообщениями Telegram. Бэкапа нет (решение 2026-11-16), и хранить их вечно незачем. Записи старше срока хранения удаляются раз в сутки.

Что удалять, решает herald: команда `bun run purge`. Когда запускать и куда сообщать результат, решает server-ops: служба `herald-retention` с cron и статус-контрактом. Строка о результате попадает в отчёты health-check, а сбой или пропуск запуска даёт алерт.

## Политика (срок R, по умолчанию 14 дней)

| Что | Удаляется |
|---|---|
| Сессия | последнее обращение агента старше R. Вместе с ней — её вопросы (и открытые), входящие (и непрочитанные), связи с сообщениями, выбранный адресат `/sessions` |
| Вопрос `answered` / `decided` | задан раньше R |
| Вопрос `open` | только с сессией: агент без таймаута может ждать сколько угодно |
| Прочитанное входящее | прочитано раньше R |
| Связь с сообщением | связь вопроса или входящего — вместе с ними; связь уведомления — старше R |
| `telegram_offset` | никогда |

## Функциональные требования

1. `bun run purge [--days N] [--dry-run]` в каталоге herald (`.env`, `HERALD_DB`). Срок — `--days`, иначе `HERALD_RETENTION_DAYS`, иначе 14. Вывод — JSON `{ cutoff, days, dryRun, deleted, remaining, dbBytes }`; код 0 при успехе, 1 при ошибке (текст в stderr). `--dry-run` считает, но ничего не удаляет.
2. Очистка идёт одной транзакцией и безопасна при работающем сервере (WAL, `busy_timeout`).
3. Связь с сообщением знает время создания (миграция v5).
4. Кнопка на удалённом вопросе — всплывающее «⚠️ вопрос устарел и удалён». Reply на удалённое сообщение — «Кому?», как сейчас.
5. Служба server-ops `herald-retention`: cron раз в сутки, вызывает purge и пишет `state/herald-retention/status.json` (`ok` — счётчики; `crit` — ошибка и `ops_notify`). `max_age_min` — 26 ч.

## Вне рамок

- `VACUUM`: данных мало, свободные страницы SQLite займёт заново.
- Общий «контракт очистки» для всех `/srv/*` в server-ops — когда появится второй такой сервис.

## Критерии приёмки

1. Тесты хранилища покрывают каждую строку политики.
2. `bun run purge --dry-run` на проде показывает счётчики и ничего не удаляет.
3. Служба `herald-retention` стоит в cron; после ручного прогона `40-statusfiles` показывает строку 🟢 herald-retention.
4. Документы обновлены: `docs/model.md` (раздел «Хранение»), `docs/deploy.md`, `docs/install.md`; в server-ops — README службы и таблица служб.
